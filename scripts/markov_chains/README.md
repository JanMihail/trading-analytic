Логика ядра подтверждена тестами, включая критичный момент — консистентность при разбиении на чанки (то есть чекпоинты между батчами не портят результат). Файлы готовы.## Как запустить

```bash
pip install -r requirements.txt

# 1) создать таблицы (через clickhouse-client или любой SQL-клиент)
clickhouse-client --multiquery < schema.sql

# 2) отредактировать config.yaml (host/port/user/symbol/threshold)

# 3) запустить нарезку
python3 build_markov_chains.py --config config.yaml
```

Полезные флаги:
- `--dry-run` — прогнать и посчитать статистику без записи в ClickHouse (проверить скорость/логи перед боевым запуском на 1 млрд+ строк).
- `--reset` — стереть чекпоинт и ранее посчитанные движения для этой пары symbol+threshold и начать нарезку с начала таблицы.

Повторный запуск без флагов **безопасно продолжит** с места последнего чекпоинта — это же используется для регулярной дозагрузки новых тиков, без переобработки всей истории.

Что я проверил тестами перед тем как отдать вам код (все выполнены в этой сессии, не «на словах»):
1. Монотонный аптренд с шагом 0.0005 при threshold=0.001 даёт ровно UP,UP,UP,UP — как вы и ожидали.
2. Разбиение той же серии на крошечные чанки даёт **идентичный** результат — то есть перенос состояния (anchor) через границы блоков/чекпоинтов не ломает нарезку (это самое опасное место в потоковых алгоритмах с чекпоинтами).
3. Разворотный паттерн (UP → DOWN → UP) считается верно.
4. Шум ниже threshold ничего не эмитит.
5. Именно функции из финального `build_markov_chains.py` (`process_block`, `moves_to_rows`, `ms_to_dt`/`dt_to_ms`) прогнаны end-to-end через симуляцию границы чекпоинта — совпадение с ожидаемым результатом.
